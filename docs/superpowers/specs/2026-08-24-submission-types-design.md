# 宿題提出管理アプリ — ステップ2「提出物マスタ + 締切設定」設計書

作成日: 2026-08-24

## 1. 背景とスコープ

小学5年1クラス（34人）の担任1名が、朝の会の前に宿題の提出をQRコードでチェックするアプリ。ステップ1で生徒名簿とQRカード印刷が完成している。本設計書は**ステップ2「提出物マスタ + 締切設定」のみ**を対象とする。

ステップ2の完了条件は、**先生が「計算ドリル」「音読カード」などの提出物を登録し、それぞれに締切時刻と提出曜日を設定できる状態**になること。

### スコープ外
- QRスキャン・複数選択モード（ステップ3）
- 提出記録の保存（ステップ3）
- 未提出者一覧・履歴集計・自動未提出確定（ステップ4）
- **休校日・行事で提出が無い日の扱い**（ステップ4で集計の実態を見ながら決める）
- JSON/CSVエクスポート・インポート（ステップ5）
- PWA化（ステップ6）

### ステップ1からの前提

以下は完成済みで、本ステップでは変更しない。

- `cohorts`（年度＋クラス）、`students`、`settings` の3ストア。DBバージョン1
- `getDb()`、`resetDbForTests()`、`ValidationError`、`StorageUnavailableError`、`newId()`
- `CohortGate` / `useActiveCohort()`、`FullScreenMessage`、`ConfirmDialog`、`AppHeader`
- `useAsync(load, key)`、`useSetting(key)`
- 配色5トークン、書体3種、印刷CSS

## 2. データモデル

IndexedDB を**バージョン2**に上げ、`submissionTypes` ストアを追加する。既存3ストアのスキーマは変更しない。

### 2.1 `submissionTypes`（提出物）

```ts
type SubmissionStatus = "active" | "ended";

type SubmissionType = {
  id: string;            // uuid
  cohortId: string;      // 年度＋クラス単位
  name: string;          // 例: "計算ドリル"
  deadline: string;      // "HH:mm" 24時間表記。例: "08:15"
  weekdays: number[];    // 0=日曜 〜 6=土曜。保存時に昇順へ整列し重複を除く
  status: SubmissionStatus;
  order: number;         // 表示順。小さいほど上
  createdAt: number;     // epoch ms
};
```

- keyPath: `id`
- インデックス: `by-cohort`（`cohortId`）

**設計判断:**

1. **`cohortId` を持つ。** 提出物はクラスごとに異なり、年度が変われば作り直す。生徒と同じ単位で揃えることで、年度アーカイブ（ステップ4以降）が一貫する。年度更新時に提出物は引き継がない。

2. **`deadline` は `"HH:mm"` の文字列。** `Date` 型だと日付が付随し、「毎日この時刻」という意味を表せない。文字列なら曖昧さがなく、`<input type="time">` の値をそのまま保存できる。

3. **`weekdays` は数値配列。** `0`〜`6` は JavaScript の `Date.getDay()` と一致させ、変換を挟まない。**空配列は保存を拒否する** — 提出日が無い提出物は未提出者一覧に永久に現れず、設定ミスとしか解釈できないため。

4. **`order` を今回から持つ。** スキャン画面（ステップ3）は朝の数分で操作するため、先生が並び順を決められる必要がある。後から追加するとデータ移行が要るので、この時点で入れる。

5. **一意性制約はインデックスで課さない。** 名前の重複禁止は「終了済みを含む」「大文字小文字・前後空白を正規化して比較」という条件付きであり、IndexedDB の unique インデックスでは表現できない。データ層の関数内で検証する。

### 2.2 DBマイグレーション

`upgrade` コールバックで `oldVersion` を見て段階的に適用する。

```ts
upgrade(db, oldVersion) {
  if (oldVersion < 1) {
    // 既存のcohorts / students / settings の作成
  }
  if (oldVersion < 2) {
    const types = db.createObjectStore("submissionTypes", { keyPath: "id" });
    types.createIndex("by-cohort", "cohortId");
  }
}
```

**既存データを削除しない。** バージョン1のDBを持つ端末で開いたとき、生徒名簿が失われてはならない。これはテストで明示的に検証する（§6）。

## 3. 画面仕様

ルート追加:

| パス | 画面 |
|---|---|
| `/submissions` | 提出物の一覧 |
| `/submissions/new` | 提出物を追加 |
| `/submissions/:id/edit` | 提出物を編集 |

いずれも `CohortGate` の内側に置く。cohortが無ければ `/setup` にリダイレクトされる。

### 3.1 提出物一覧 `/submissions`

`AppHeader` を表示し、副題は `提出物3件・終了1` の形式にする。名簿の `在籍33人・欠番1` と同じ構文にすることで、先生が2つの画面で違う読み方を覚えずに済む。

各行に表示するもの:
- 提出物名
- 締切時刻（`font-num`）
- 提出曜日（`月火水木金` のように連結。すべて選択なら `毎日`）

状態の描き分けは名簿のセルと同じ規則にする:

| 状態 | 表示 |
|---|---|
| 有効 | 藍の枠線＋墨の文字 |
| 終了 | 方眼色の破線枠＋方眼色の文字、背景に薄いハッチ、名前の後ろに `（終了）` |

- 行をタップすると `/submissions/:id/edit`
- 下部に `提出物を追加`
- 提出物が0件のときは「まず提出物を追加してください」と追加ボタンを表示する

**並べ替え**は、各行の「上へ」「下へ」ボタンで行う。ドラッグ&ドロップは採用しない — タッチ操作でのドラッグは実装が重く、朝に片手で扱う場面では誤操作しやすい。ボタンなら押した結果が確実である。終了した提出物は並べ替えの対象外（末尾にまとめて表示する）。

### 3.2 提出物を追加 `/submissions/new`

- **名前**: 自由入力テキスト。プレースホルダ `計算ドリル`
- **締切時刻**: `<input type="time">`。初期値 `08:15`
- **提出曜日**: 7つのトグルボタン（日月火水木金土）。初期値は月〜金が選択済み
- `order` は既存の提出物（終了したものを含む）の最大値 + 1 を自動で割り当てる。有効なものだけで数えると、終了した提出物の `order` と衝突しうるため

保存後 `/submissions` へ戻る。

**曜日をトグルボタンにする理由**: チェックボックスの列より押しやすく、選択状態が一目で分かる。朝の教室で片手で操作する前提に合う。各ボタンは44px四方以上を確保し、`aria-pressed` で選択状態を伝える。

### 3.3 提出物を編集 `/submissions/:id/edit`

- 名前・締切時刻・提出曜日を変更できる
- **終了にする**: `status` を `ended` に変更する。過去の提出記録（ステップ3以降）と集計には残る。確認ダイアログを表示
- **有効に戻す**: 終了済みのものに表示する
- **完全に削除**: レコードを物理削除する。確認ダイアログで「この提出物の記録は元に戻せません」と明示し、終了との違いを画面上で説明する

生徒の編集画面と同じ構造・同じ文言の枠組みにする。先生が2つの画面で違う操作体系を覚えずに済むため。

### 3.4 名簿からの導線

名簿画面の下部ボタンに `提出物の設定` を追加する。現在の `生徒を追加` `QRを印刷` と合わせて3つになる。375px幅で3つ並ぶと窮屈なため、**2行に分ける**（1行目に `生徒を追加`、2行目に `QRを印刷` と `提出物の設定`）。

## 4. 視覚デザイン

ステップ1のトークンをそのまま使う。新しい色・書体は追加しない。

- 配色5トークンのみ: 画用紙 `#FBFAF7` / 墨 `#1A1A1F` / 藍 `#22406B` / 方眼 `#C9D6E4` / 朱 `#D8452E`
- **朱は「完全に削除」の確認ダイアログのみ**。トリガーには使わない
- Tailwind素のカラーは使わない
- 締切時刻は `font-num`、画面見出しは `font-display`
- 曜日トグルは選択時が藍の塗り＋画用紙の文字、非選択時が方眼色の枠線＋墨の文字
- スマホ幅375pxで7つの曜日トグルが1行に収まること。375px から左右のパディング16px×2を引いた343pxが使える幅で、**44px × 7 + 間隔4px × 6 = 332px** なので11pxの余裕がある。ボタンを大きくする場合はこの式を計算し直すこと

## 5. バリデーションとエラー処理

| 状況 | 挙動 |
|---|---|
| 名前が空 | 「提出物の名前を入力してください」 |
| 名前が重複（終了済みを含む） | 「計算ドリルはすでに登録されています」。終了済みとの重複なら「計算ドリルは終了した提出物として登録されています」と理由を示す |
| 曜日が未選択 | 「提出する曜日を1つ以上選んでください」 |
| 締切時刻が未入力・不正 | 「締切時刻を入力してください」 |
| IndexedDBが使用不可 | ステップ1と同じ全画面エラー |

名前の比較は `name.trim().normalize("NFKC").toLowerCase()` で正規化してから行う。`NFKC` で全角・半角の差（例: `ﾄﾞﾘﾙ` と `ドリル`）を吸収する。集計画面で見分けのつかない同名が2つ並ぶと、先生がどちらを見ているか判断できないため。**保存する `name` は正規化前の入力そのまま**とする。表示は先生が打った通りであるべきなので、正規化は比較のためだけに使う。

エラー文は何が起きたかと次にどうするかを示す。謝らない。全画面エラーには名簿へ戻る導線を置く。

## 6. テスト方針

TDDで進める。実装前にテストを書く。

**マイグレーション**（最重要）
- バージョン1のDBに生徒を入れた状態でバージョン2に上げ、**生徒データが残ること**
- バージョン2で `submissionTypes` ストアとインデックスが作られること
- 新規の端末（DBなし）でバージョン2として正しく作られること

**データ層**
- 提出物の追加・更新・終了・復帰・物理削除
- 名前の重複が拒否されること（有効・終了の両方に対し、文言が異なること）
- 空配列の曜日が拒否されること
- `order` の自動採番と並べ替え（上へ・下へ）
- 別cohortとは名前が重複してもよいこと

**コンポーネント**
- 一覧が有効と終了を描き分けること
- 曜日の表示（すべて選択なら `毎日`）
- 曜日トグルの選択状態が `aria-pressed` に反映されること
- 0件のときの空状態
- 並べ替えボタンで順序が入れ替わること。先頭の「上へ」と末尾の「下へ」が無効であること

## 7. 決定事項の要約

1. 提出物は曜日を持つ。空配列は不可。
2. 使わなくなった提出物は「終了」にする。物理削除も明示的に選べる。生徒の転出と同じ構造。
3. 並び順（`order`）を今回から持つ。後から足すとデータ移行が要るため。
4. 締切時刻は `"HH:mm"` 文字列。`Date` は使わない。
5. 休校日の扱いはステップ4に送る。
6. 並べ替えはボタン方式。ドラッグ&ドロップは採用しない。
