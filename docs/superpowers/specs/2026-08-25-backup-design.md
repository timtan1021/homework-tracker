# 宿題提出管理アプリ — ステップ5「バックアップ・復元」設計書

作成日: 2026-08-25

## 1. 背景とスコープ

ステップ1〜3・6で名簿・提出物マスタ・スキャン・PWA化が完成している。本設計書は**ステップ5「バックアップ・復元」のみ**を対象とする。

### なぜステップ4より先にやるか

これまでDBの構造変更を3回行っている（バージョン1→2→3）。**まだ復旧手段が無い。** `docs/手元での確認手順.md` にも「消えていたらすぐ教えてください」と書き続けている状態で、これを積み上げるほど危険が増す。集計より先に安全網を張る。

ステップ5の完了条件は、**先生が現在のクラスのデータをファイルに書き出し、別の端末（または壊れた後の同じ端末）に読み込んで復元できる状態**になること。

### スコープ外
- 未提出者一覧・履歴集計・自動未提出確定（ステップ4）
- 過去年度のアーカイブを含めた一括バックアップ（未実装の年度更新機能と重なるため対象外）
- CSV出力（仕様書には記載があるが、復元に使わない形式のため見送る。理由は §2）

### ステップ1〜3・6からの前提

- `cohorts` / `students` / `settings` / `submissionTypes` / `submissions` の5ストア。DBバージョン3
- `CohortGate` / `useActiveCohort()`、`SetupGate`、`ConfirmDialog`（`tone="danger"` で朱を使う）、`FullScreenMessage`
- `/settings` は「氏名を表示する」のトグルのみを持つ
- `/setup` は年度・クラス名を入力してcohortを作る画面のみを持つ

## 2. ファイル形式

JSONのみを対象とする。CSVは表計算ソフトで開く用途であり、復元用のファイル形式としては別物になる。仕様書は両方を求めているが、**復元できることが本質**であり、閲覧用のCSVは今回見送る。

```ts
type BackupFile = {
  formatVersion: 1;
  /** 書き出した日時。ISO文字列。表示用で、復元の判断には使わない。 */
  exportedAt: string;
  cohort: Cohort;
  students: Student[];
  submissionTypes: SubmissionType[];
  submissions: Submission[];
};
```

**`formatVersion` をDBの `DB_VERSION` とは独立に持つ。** 将来ファイル形式だけを変えたい場合（DBのスキーマは変えずに）に備える。読み込み時にこの番号を検証し、知らない値なら復元を拒否する。

**IDは元のまま書き出し、元のまま復元する。** 生徒・提出物・提出記録の紐付け（`cohortId` や `studentId` の参照）はIDで表現されているため、振り直すと参照を作り直す処理が要る。元のIDのまま入れ直せば、書き出し時に整合していたデータはそのまま整合する。

### ファイル名

`宿題管理_バックアップ_20260825.json` の形式にする。クラス名を含めることも検討したが、ファイル名に使えない文字（`/` 等）を含みうるため含めない。日付は `toDateKey`（ステップ3で作成済み、ローカル日付を返す）を流用する。

## 3. 書き出し（`/settings`）

設定画面に「バックアップ」の節を追加する。

- ボタン1つでその場でダウンロードされる。`Blob` と `<a download>` を使う。サーバーへは一切送らない
- 書き出す内容は現在アクティブなcohortに紐づく全データ

## 4. 復元（2箇所に置く）

### 4.1 `/settings` から

通常の使い方。**現在のデータを完全に置き換える。** 破壊的な操作であることを示し、確認ダイアログを挟む。

```
現在のデータ（2026年度 5年1組）を消して、
選んだファイルの内容に置き換えます。
元に戻せません。
```

**朱の使用範囲をここで1つ広げる。** これまで「花丸と『完全に削除』の確認ダイアログのみ」としてきたが、復元は「全データを問答無用で消す」という点で完全削除と同格の重さを持つ。既存の `ConfirmDialog` の `tone="danger"` を流用するだけで、新しい仕組みは増えない。制約の記述を「花丸と、完全に元へ戻せない操作（完全削除・復元）の確認ダイアログ」に更新する。

### 4.2 `/setup` から

**機種変更のときの本来の使い方。** 新しい端末にはまだクラスが無く、`CohortGate` が `/settings` への到達を防ぐ（`/setup` へリダイレクトされる）。復元の主目的である「機種変更」に、既存の設計のままでは遠回りが必要になる。

`/setup` に「クラスをつくる」フォームと並べて「バックアップから復元する」の導線を置く。ファイルを選ぶと即座に検証・復元する。

**この経路では確認ダイアログを出さない。** `SetupGate` により、この画面に到達できるのは有効なcohortが存在しないときだけであり、消える現在のデータが無い。確認を求める意味がない。

### 4.3 復元の内部処理

1. 現在アクティブなcohortと、それに紐づく生徒・提出物・提出記録をすべて削除する（`/setup` 経由では通常この手順は空振りする）
2. バックアップファイルの内容を、元のIDのまま挿入する
3. cohortの `isActive` を `true` にする

**過去に残っている無効化済みのcohort（もしあれば）には触れない。** 触るのは現在アクティブな1件の周辺だけである。

## 5. 検証とエラー

| 状況 | メッセージ |
|---|---|
| ファイルがJSONとして壊れている | 「このファイルは読み込めませんでした。バックアップファイルを選び直してください」 |
| `formatVersion` が未知・欠落 | 「対応していない形式のバックアップです。最新版のアプリで書き出したファイルを使ってください」 |
| 必須項目が欠けている・型が合わない | 上記2つ目のメッセージで統一する。先生に内部構造の違いを説明しても意味がないため、原因を問わず同じ案内にする |

エラー文は何が起きたかと次にどうするかを示す。謝らない。

## 6. 視覚デザイン

新しい色・書体は追加しない。復元の確認ダイアログは既存の `ConfirmDialog` をそのまま使う。

`/setup` の追加導線は、既存フォームの下に控えめに置く。年度・クラス名の入力欄より目立たせない（先生が意図せず復元を選んでしまわないようにするため）。

## 7. テスト方針

**ファイルのダウンロード・選択自体はブラウザAPIであり自動テストに向かない。** そのため、検証ロジックと復元処理を純粋関数として切り出し、UIから独立にテストする。

**データ層**
- 書き出しがcohortと関連4種のレコードを正しく集めること
- 復元が現在のデータを消して置き換えること。IDが保たれること
- `formatVersion` の検証が壊れたファイル・未知のバージョンを拒否すること
- 復元後、他の（無効化済みの）cohortに影響しないこと

**画面**
- `/settings` の復元が確認ダイアログを経ること
- `/setup` の復元が確認ダイアログ無しで即座に進むこと
- 不正なファイルを選んだときにエラーが出て、データが変わらないこと

## 8. 決定事項の要約

1. 対象は現在のcohortのみ。過去年度アーカイブは含めない
2. ファイル形式はJSONのみ。CSVは見送る
3. 復元は現在のデータを完全に置き換える。IDは元のまま保つ
4. 復元は `/settings` と `/setup` の2箇所に置く。`/setup` 側は確認ダイアログ無し（消えるデータが無いため）
5. 朱の使用範囲を「花丸・完全削除」から「花丸・完全に元へ戻せない操作（完全削除・復元）」に広げる
