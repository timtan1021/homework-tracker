# 宿題提出管理アプリ — ステップ3「スキャン画面 + 複数選択モード」設計書

作成日: 2026-08-24

## 1. 背景とスコープ

小学5年1クラス（34人）の担任1名が、朝の会の前に宿題の提出をチェックする。ステップ1で生徒名簿とQRカード印刷、ステップ2で提出物マスタと締切・曜日設定が完成している。本設計書は**ステップ3「スキャン画面 + 複数選択モード」のみ**を対象とする。

ステップ3の完了条件は、**先生がQRカードを読んで提出を記録できる状態**になること。この画面が毎朝使う主画面になる。

### スコープ外
- 未提出者一覧・履歴集計・自動未提出確定（ステップ4）
- 休校日の扱い（ステップ4）
- JSON/CSVエクスポート・インポート（ステップ5）
- PWA化・ホスティング（ステップ6）

### ステップ1〜2からの前提

- `cohorts` / `students` / `settings` / `submissionTypes` の4ストア。DBバージョン2
- `CohortGate` / `useActiveCohort()`、`FullScreenMessage`、`ConfirmDialog`、`AppHeader`、`WeekdayPicker`
- `useAsync(load, key)`、`useSetting(key)`、`useStudents`、`useSubmissionTypes`
- `buildQrPayload(studentId)` — `hw1:<uuid>` を返す。**対になる解析関数はまだ無い**
- 配色5トークン、書体3種

## 2. 配信の前提（設計を左右する制約）

**カメラは HTTPS でしか使えない。** ブラウザの `getUserMedia` はセキュアコンテキスト限定で、`http://192.168.x.x` のようなLAN配信では利用できない。ポリフィルも回避策も存在しない（ステップ1の `crypto.randomUUID` は自前で代替できたが、カメラは代替できない）。

開発時の `localhost` は例外的にセキュアコンテキスト扱いなので動作する。`npm run dev --host` でのLAN配信では動作しない。

したがって実運用は HTTPS ホスティング（ステップ6）が前提となる。

### 2.1 カメラが使えないときの代替手段

**「番号でチェック」モードを常設する。** カメラ失敗時の退避ではなく、いつでも切り替えられる同格の入力手段として置く。

理由:

1. **このアプリは紙のチェックリストを置き換える。** カメラが動かない日に「今日は宿題チェックができません」では、先生は代わりを持たない。権限拒否、カメラ故障、HTTPで開いてしまった、レンズが汚れている — いずれも実際に起きる。
2. **カードを忘れた生徒が必ず出る。** ラミネートしたカードをドリルごと家に置いてきた生徒を、カメラ方式だけでは記録できない。
3. **テストできる。** カメラ層は自動テストできないが、番号タップの経路は完全にテストできる。記録処理の本体がUI経由で検証されることになる。

カメラが使えないと判明した時点で自動的にこのモードへ切り替え、理由を画面に出す。黙って何も映らないと、先生は端末の故障と考える。

## 3. データモデル

DBを**バージョン3**に上げ、`submissions` ストアを追加する。既存4ストアのスキーマは変更しない。

### 3.1 `submissions`（提出記録）

```ts
type Submission = {
  id: string;              // uuid
  cohortId: string;
  studentId: string;
  submissionTypeId: string;
  date: string;            // "YYYY-MM-DD" ローカル日付
  submittedAt: number;     // epoch ms。最初に提出した時刻
};
```

- keyPath: `id`
- インデックス:
  - `by-cohort-date`（`["cohortId", "date"]`）— その日の一覧を引く
  - `by-unique`（`["date", "studentId", "submissionTypeId"]`、**unique**）— 二重記録を防ぐ

**設計判断:**

1. **`date` は `"YYYY-MM-DD"` の文字列。** 提出は「その日の提出」であって時刻の連続量ではない。`Date` を持つとタイムゾーンや時分の差で同日判定が壊れる。日付の境界はローカル時刻で切る — 先生の教室の日付が正しい日付である。

2. **`by-unique` を unique インデックスにする。** 二度スキャンの防止をアプリのロジックだけに任せると、カメラの連写や二重タップで抜ける。DBの制約を最後の砦にする。

3. **`submittedAt` は最初の提出時刻を保つ。** 二度目のスキャンで上書きしない。締切前に出した生徒が、先生の再スキャンで遅刻扱いになってはならない。

4. **未提出のレコードは作らない。** 「提出記録が無い＝未提出」で表す。34人 × 提出物 × 日数のレコードを毎日作るのは無駄で、締切前と未提出の区別もつかなくなる。締切超過の判定はステップ4で締切時刻と突き合わせて行う。

### 3.2 QRペイロードの解析

ステップ1で `buildQrPayload(studentId)` を作ったが、対になる解析関数は「スキャナはステップ3」として意図的に省いていた。ここで追加する。

```ts
function parseQrPayload(payload: string): string | null
```

`hw1:` で始まらない文字列は `null` を返す。商品バーコードや他アプリのQRを黙って弾くための接頭辞である。

## 4. 画面仕様

ルート追加: `/scan`（`CohortGate` の内側）

### 4.1 レイアウト

```
┌─────────────────────────────┐
│ 8月24日(月)         名簿へ  │
│ ─────────────────────────── │
│ ┌───────┐┌───────┐         │← 今日が提出日のものだけ
│ │計算ドリル││音読カード│         │  タップでON/OFF
│ │ 8:15  ││ 8:15  │         │  ONは藍の塗り
│ └───────┘└───────┘         │
│                             │
│ ┌─────────────────────────┐ │
│ │      カメラ映像          │ │← 番号モードでは
│ │                         │ │  出席番号グリッド
│ └─────────────────────────┘ │
│      ［番号でチェック］       │
│                             │
│         12番                │← 直前の結果
│      （花丸）提出しました      │
│                             │
│ 計算ドリル 8人・音読カード 5人 │← 今日の進捗
└─────────────────────────────┘
```

### 4.2 提出物の選択

**その日の曜日に合う提出物だけを並べる。** 火曜日に「日記（月曜のみ）」は出さない。選択肢が減るほど朝の誤操作が減る。

- 初期状態は**全部ON**。毎朝すべてを確認するのが通常であり、先生が毎回選び直す手間を省く
- 最低1つはONでなければスキャンを受け付けない
- 終了した提出物（ステップ2の `ended`）は出さない
- その日に提出物が1つも無ければ、その旨を表示してスキャンを無効にする

### 4.3 スキャンの結果

| 状態 | 表示 | 記録 |
|---|---|---|
| 提出を記録 | 花丸＋「12番 提出しました」 | 選択中の全提出物に記録 |
| すでに提出済み | 「12番 提出済み」（花丸なし） | 変更しない |
| 一部だけ提出済み | 花丸＋「12番 提出しました」 | 未記録のものだけ追加 |
| 転出した生徒 | 「12番は転出しています」 | 記録しない |
| 別クラス・別年度のQR | 「このクラスの生徒ではありません」 | 記録しない |
| `hw1:` で始まらない | 何も起きない | 記録しない |

**同じQRを連続で読み続ける対策**: 直前に読んだIDと同じものは2秒間무視する。カメラは毎フレーム同じカードを認識するため、これが無いと結果表示が点滅し続ける。

### 4.4 花丸

スキャンで新たに記録できたとき、結果表示部に朱色の花丸をSVGストロークで描く。約450ms、円は速く花弁はゆっくり。

**朱がここで初めて本来の意味で使われる。** ステップ1・2では削除確認だけに使ってきたが、設計当初からの意図は先生の朱ペンだった。トーストも「✓」も出さない。丸がつく、それだけにする。

`prefers-reduced-motion` のときはアニメーションせず完成形を即座に表示する。

### 4.5 番号でチェックするモード

カメラ映像の代わりに、名簿と同じ出席番号のグリッドを出す。

- 在籍中の生徒のみ。転出者は出さない
- 番号をタップすると、選択中の提出物に記録する。結果表示はスキャンと同じ
- **すでに全部提出済みの番号は、セルに花丸の印を小さく添える**。誰がまだかを一目で見せる
- カメラモードとはボタンで相互に切り替えられる

### 4.6 導線

名簿画面の下部ボタンの先頭に `提出チェック` を置く。毎朝使う画面なので、最も押しやすい位置と塗りのボタンにする。

**ステップ6で `/scan` をホームにすることを検討する。** 毎朝の利用で名簿を経由するのは無駄だが、提出物が未登録の状態でスキャン画面に着地すると行き詰まるため、今回は名簿をホームのままにする。

## 5. 技術選定

**QRの解析は `jsQR`（1.4.0）を使う。** 依存ゼロ、型定義同梱、Apache-2.0。「画像データを渡すとQRを返す」だけの純粋な関数で、描画も権限管理も持ち込まない。

`html5-qrcode` は高機能だが独自のUIを持ち込むため、この画面の設計（花丸、複数選択バー、番号モード）と衝突する。採用しない。

カメラは `getUserMedia({ video: { facingMode: "environment" } })` で背面カメラを要求し、`requestAnimationFrame` でフレームを `<canvas>` に描いて `jsQR` に渡す。

## 6. 視覚デザイン

ステップ1のトークンをそのまま使う。新しい色・書体は追加しない。

- 配色5トークンのみ。**朱は花丸と削除確認ダイアログのみ**
- 朱は18pt以上でのみ使う（コントラスト比が約4.3:1のため）。花丸はグラフィックなので対象外
- 出席番号は `font-num`、見出しは `font-display`
- 提出物のトグルはONが藍の塗り＋画用紙の文字、OFFが方眼色の枠線＋墨の文字
- タップ領域は44px四方以上
- カメラ映像は正方形に切り、画面幅に対して最大320pxとする。大きすぎると提出物の選択と結果表示が画面外に出る

## 7. バリデーションとエラー処理

| 状況 | 挙動 |
|---|---|
| カメラの権限を拒否された | 「カメラを使えません。端末の設定で許可するか、番号でチェックしてください」と表示し、自動的に番号モードへ切り替える |
| カメラが存在しない・HTTPで開いた | 「この開き方ではカメラを使えません。番号でチェックしてください」と表示し、番号モードへ切り替える |
| 提出物が未選択 | 「チェックする提出物を選んでください」。スキャンを受け付けない |
| その日に提出日の提出物が無い | 「今日が提出日の宿題はありません」。スキャンを無効にする |
| 提出物が1件も登録されていない | 「まず提出物を登録してください」と提出物設定への導線を出す |
| IndexedDBが使用不可 | ステップ1と同じ全画面エラー |

エラー文は何が起きたかと次にどうするかを示す。謝らない。

## 8. テスト方針

TDDで進める。

**カメラ層は自動テストできない。** そのため、記録処理を**ペイロード文字列を受け取る純粋な関数**として切り出し、カメラ層と分離する。

```ts
recordSubmission(input: {
  cohortId, studentId, submissionTypeIds, date
}): Promise<RecordResult>
```

`RecordResult` は `{ kind: "recorded" | "already" | "transferredOut" | "notFound"; student?: Student }`。画面はこの結果を表示に変換するだけにする。

**マイグレーション**
- バージョン2のDBに生徒と提出物を入れた状態でバージョン3に上げ、**両方が残ること**
- 新規端末でバージョン3として4+1ストアが作られること

**データ層**
- 提出の記録、二度目が上書きしないこと、`submittedAt` が保たれること
- 転出した生徒、別cohortの生徒を弾くこと
- 複数の提出物にまとめて記録できること
- 一部だけ提出済みのとき、未記録のものだけ追加すること
- unique インデックスが二重記録を防ぐこと

**ペイロード解析**
- `hw1:` で始まらない文字列が `null` になること
- `buildQrPayload` の出力を `parseQrPayload` で元に戻せること

**画面**（番号モードで検証する。カメラを使わずに記録処理の本体を通せる）
- 提出物の選択が曜日で絞られること
- 未選択ならスキャンできないこと
- 番号をタップすると記録され、結果が出ること
- 二度目が「提出済み」になること
- 提出済みの番号に印が付くこと
- 進捗の人数が増えること

## 9. 決定事項の要約

1. カメラは HTTPS 必須。LAN配信では動かない。ステップ6のホスティングが前提。
2. 「番号でチェック」を常設する。カメラ失敗時の退避ではなく同格の入力手段。
3. 二度目のスキャンは上書きせず「提出済み」と知らせる。
4. その日の曜日に合う提出物だけを並べる。
5. 未提出のレコードは作らない。記録が無いことで表す。
6. `date` は `"YYYY-MM-DD"` 文字列。ローカル日付で切る。
7. QR解析は `jsQR`。UIを持ち込まない純粋な関数だから。
8. 朱は花丸で本来の用途に戻る。
